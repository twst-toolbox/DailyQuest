# 扭曲仙境（日服）任务流分析

> 依据 2026-10-18 用户提供的 4 张实机截图（蓝叠，横屏 1920×1080 比例）整理。
> 本文档是"上课清体力"任务的脚本设计底稿。

## 包名
- 日服：`com.aniplex.twst.jp`
- 美服：`com.aniplex.twst.en`

## 完整流程拆解（用户提议的测试链路，已确认可自动化）

| # | 画面 | 动作 | 识别依据（模板锚点） |
|---|---|---|---|
| 1 | 桌面 | 启动游戏 | 包名 launch |
| 2 | 标题画面 | 点任意处进入 | 标题 LOGO / "TOUCH"提示区域 |
| 3 | （可能）公告/登录奖励/下载确认 | 逐个点关闭/OK | 通用弹窗关闭按钮（×、閉じる、OK） |
| 4 | 主页 | 验证到达 → 点 LESSON | 左上 RANK 徽章 = 主页锚点；右侧 LESSON 镜框按钮 |
| 5 | 寮選択 | 选「通常」或「日替わり」标签 → 点目标寮卡片 | 顶部标签；寮卡片（Heartslabyul 等） |
| 6 | 授業編成 | 点右下 START | START 紫按钮（含 AP 消耗角标） |
| 7 | 上课中 | 点 AUTO（必要时 LOOP）→ 等待结算 | 右上 AUTO/LOOP 按钮；回合数圆盘 |
| 8 | 结算画面 | 连点跳过奖励/经验结算 | 结算锚点（结果标题/NEXT 按钮） |
| 9 | 判断体力 | 若 AP 足够 → 回到 5 继续；不足则退出循环 | START 按钮上的 AP 角标 / 体力不足弹窗 |
| 10 | 主页 | 按退回键 → 退出确认对话框点"是" | 系统 BACK + 退出确认弹窗 |

**好消息：图 4 显示上课自带 `AUTO` 和 `LOOP` 按钮**——官方内建自动，自动化只需"点进课程、开 AUTO、等结算、点继续"，全程点击很少，是理想的首个测试任务。
另外上课可无限重复（不像签到每天一次），正好满足"反复调试"的需求，签到只是每日队列里的第一步。

## 需要录入的模板（约 12 张，录制模式可搞定）
- 标题 LOGO、主页 RANK 锚点、LESSON 按钮
- 寮選択标签×2、目标寮卡片
- START 按钮、AUTO 按钮、LOOP 按钮
- 结算锚点、NEXT/OK 通用按钮、通用关闭 ×
- 体力不足弹窗锚点、退出确认"はい"按钮

## 必须处理的异常分支（脚本引擎的"通用弹窗处理"）
1. 通信エラー → リトライ 弹窗（网络波动常见）
2. 每日 4:00(UTC+9) 重置弹出的日期变更提示
3. 活动横幅/公告数量不固定 → 用"反复点关闭直到主页锚点出现"的循环，而不是数次数
4. 维护中画面 → 识别后中止任务并在日志标注（不要狂点）
5. 游戏强制更新 → 中止并提示

## OCR 在这类游戏上的定位（重要结论）
用户实测 PaddleOCR / Tesseract 效果差，原因：这类 UI 大量使用**哥特体/装饰字体**（看图 1 的 "LESSON"、图 2 的寮名花体字），通用 OCR 对艺术字本就弱。

对策（与 MAA 相同思路）：
- **按钮、图标、弹窗一律用模板匹配，不走 OCR** —— 艺术字反而是极好的匹配特征，模板匹配几乎 100% 可靠。
- OCR 只用于读"数值"（如体力 10/10），且采用**先模板定位区域、再对小区域 OCR** 的方式（即用户设想的"识图之后再 OCR"，这是正确架构）。
- 连数值都可以不用 OCR：体力是否足够可以通过"点 START 后是否弹出体力不足弹窗"来判断（行为判断替代读数）。初期建议就用这个办法，把 OCR 推到二期。
